Some time ago i saw the 512kb club and it stuck with me. You can squeeze a bunch of stuff into 512kB! For the more austere there is even a 1kb club. But 1kb is hardmode, you get limited by the amount of text you can even squeeze into it.

1024 chars of UTF8 = 1kB ... so less than 1024 chars in total fit on the page, because some is in the html tags, metadata, maybe style and such.

This website is somewhere in between 1kB and 512kB, more on the side of 1 than 512. It makes me happy that i got the homepage in the <10kB range (not counting the favicon), but for articles like this one, thats unfeasible as the text itself starts being a factor and having some ASCII ART graphics already takes up several kilobytes.

The backbones are Askama for templating and Axum for serving and I'll go into that below.

Feel free to snoop around the complete codebase here: mic0.dev repo.

Things to consider for tiny websites:

  • Text content, markdown like HTML and CSS styles are usually very cheap.
  • Media is heavy. A single image, lets say 100kB can take as much space as 100.000 letters do on a screen. This is why i opted to go for ASCII art. It's a bit heavier than really good prepped SVGs, but with a lot more charm.
    Fellas like this one: 🫪 could also work. But thats another aesthetic in itself.
  • Javascript can easily get into absurd sizes. A library like Miden SDK, which i worked with recently, goes into several megabytes size wise. While you can certainly squeeze 20 client side routers and frameworks into 512kB im of the opinion that Websites were never meant to be fat server side rendered react apps.

  • Minimize custom fonts. Fonts can easily go into tens, hundreds of thousands of kB. This website only loads a single font: aahub-light and only on the article pages and it accounts for 45kB. Wish i could do without ... but ASCII graphics on articles would be all garbled up.

People hate on doing HTML manually because it looks dorkish and old. I think there is some kind of generational trauma attached to pure HTML+CSS. But browsers today offer very broad general support for everything. Gone are the days where one would worry how this looks in an arbitrary browser ... It's all mostly chromium now anyway.

To me HTML & CSS come easy.

Wrangling HTML with Askama

Copy-pasting same HTML for each page and just changing the <body> content works and is lean but its also a shortcut to to introduce inconsistencies is overall tedious.

Askama is a simple yet powerful template engine. It powers things like docs.rs which every Rust developer sooner or later lands on. It packs stuff into templates at compile time as much as possible, with some leeway for dynamic content. Overall its very fast on the recompilation part and the syntax is straightforward.

Furthermore it will very happily die on compilation with a meaningful error message if your templates or variables passed into them are incorrect / erroneous so you get all the good parts of Rust with it.

For a little taste how it that might look like, this is how the template for the articles, aptly named _article.html looks like:

{% extends "_layout.html" %} {%- block title -%} mic0.dev - {{ title }} {%- endblock -%} {%- block content -%}

{{title}} </h1>

by mic0, dated: {{ date_str }}</p>
{{ content | safe }}

{% match signature_to_display %} {% when 0 %} {% include "ascii/01_article_sig.html" %} {% when 1 %} {% include "ascii/02_article_sig2.html" %} {% else %} {% include "ascii/01_article_sig.html" %} {% endmatch %}

ATTRIBUTIONS

ASCII art used in the article and the above signature was sourced from AAHUB.

{%- endblock -%}

You can already observe a number of things here:

  • conditionals like match and if / else for setting different signatures at the bottom or including the syntax highlighter
  • extending templates like _layout.html that generates the metadata & holds the page's HTML skeleton
  • including other templates like CSS inserts
  • inserting dynamic content via {{ content | safe }}. (e.g. The content you are reading right now)
  • setting variables like the title of the page that other templates pick up

Askama offers a lot more, but you can take what you need and its more than enough. However it doesn't serve content ... for that we need something else.

Using Rust to make code blocks look all pretty

Its easy to throw a code snippet into a <pre> element, but you are left with a sad one-colored code. It's hard to read and looks nothing like your riced IDE.

In the traditional JS world, there are things like Highlight.js but its a chunky 80kb minified. There is a much leaner version called Microlight for code samples below is only 2.2kb in size - an acceptable compromise. But why use JS at all if we can highlight with Rust :)

I opted to use lol_html used by Cloudflare for rewriting streamed HTML and a lib called syntect used for actual coloring.

I didn't find any quick solution inside Askama itself, so for anyone with a similar challenge my end solution looks like this:

// Accepts an HTML String and Syntect settings/theme and replaces all contents // of any element found with a [data-paint] attribute fn highlight_code(html: Rc, ss: Rc, theme: Rc) -> String { rewrite_str( // from lol_html &html.clone(), RewriteStrSettings::new().append_element_content_handler(element!("div[data-paint]", { move |el| { let theme_clone = theme.clone(); let ss_clone = ss.clone(); let html_clone = html.clone(); // read the language denoted with data-paint attribute // aka [data-paint="html"] for example let paint_lang = el.get_attribute("data-paint") .unwrap_or("rust".to_string()); // get location of the content's start let inner_start = el.source_location().bytes().end; // nuke the innerHTML el.set_inner_content("", ContentType::Html); el.on_end_tag(end_tag!(move |end| { // get the content's end location let inner_end = end.source_location().bytes().start; // get the whole content from original string // now that we know where to snip it out let inner = &html_clone[inner_start..inner_end]; // use syntect to color our codeblocks let syntax = ss_clone .find_syntax_by_token(&paint_lang) .unwrap_or_else(|| ss_clone.find_syntax_plain_text()); let transformed = highlighted_html_for_string( inner, &ss_clone, syntax, &theme_clone ).expect("highlighting failed"); // insert the highlighted codeblock back into the element, // completing the swap end.before(&transformed, ContentType::Html); Ok(()) }))?; Ok(()) } })), ) .unwrap() }

Tying it up with Axum

Askama's job is to chew up the templates and their nested templates, digest it, fill in the interpolated variables and spit out a single String. All of it is then passed into Axum's Html() and voila, our dish is served to the user.

I like to use Axum because it's really fast and it has never failed me. I've been running it for years in production with zero issues. Docs.rs use it as well to serve the huge library of crate docs and references.

Route for the root of this website serving index.html looks like this:

async fn index_handler() -> Result { #[derive(Debug, Template)] #[template(path = "index.html")] struct Tmpl { articles: Vec, } let template = Tmpl { articles: get_article_metas(), }; Ok(Html(template.render()?)) }

Filling in the Askama template with variables is as simple as just constructing a struct with Template trait. Calling it's render() function gets you your packed HTML String which is then served by Axum.

And that's it.

For a quickstart of Askama + Axum I recommend you check out the official Askama + Axum example. God knows i borrowed heavily when setting it up initially.
