Websites have historically only gotten fatter. The average website now hovers around 2.5MB (google it). That's in part due to big media used, but it's also the tooling.

For the past 15 years+ the meta has been to build SPAs - single page applications. This is largely thanks to the advent of fat javascript libraries which moved the solution space from the yucky server side to the yummy client side where everything can be done on the users' computers instead.

Leave some bandwidth and CPU cycles for the phone users on the spotty WiFi fatso!

Lean websites are faster to load, offer better UX and are actually in line with what makes browsers snappy and happy.

So how did we get to the point where it feels like half of the web are React apps being spat out from a "server" rendering javascript on an engine running inside Docker inside a virtual server on a server like a matryoshka of waste?

SPA revolution and History API

I remember when pushState() came out ... a simple but powerful function that lets you control the browser's URL line and magically route the user around pages. It was and it still is fairly simple to write your own app router, but of course no one does that anymore manually because you expect $THE_FRAMEWORK to do that for you.

Frontend frameworks usually come with their own app routers, but all of these basically just use the History API or rather the pushState() function of the History API to change the url bar in the browser. It's a neat trick, not an actual route.

For this to work with your website, the server usually just returns the same index.html on each route and the javascript then quickly reads the route and constructs the correct page "on the fly" inside your browser. But well ... usually you still can notice it. Its those couple of hundreds of milliseconds to a few seconds that the page is just blank and everything is "loading".

Here is the thing: the browser that you use doesn't care for React components. It's just Javascript. All it wants is an HTML file, where there is some Javascript, markdown, metadata and CSS defined.

The History API that fundamentally enabled SPAs works best with well self-contained ... apps, not websites.

The birth of LA CREATURA (Vercel) - Server side rendering of SPA tech so you can have multi page applications

One area that SPAs traditionally and by design suck at is metadata. In the past, web crawlers like Google's crawler, didn't fancy waiting for a fat React app with React router to load in 2.6 seconds. It always read what it could from the index.html that was initially sent.

The immediate effect on SPAs for this is that it can only provide one version of the <HEAD> element with only one version of metadata. That in turn means that all your pages have the same thumbnail, same description and same "look" when you link them to your buddies or customers on the little widget that pops under your link. Hmm annoying right?

Since then indexers have gotten a bit better for sure and afaik they now wait for the page load, but that's only because the explosive growth of SPAs made them wait, not because that's how the Web was designed. This is where SSR comes in.

SSR or Server side rendering in React (or similar libs) as a tech has been around since mid 20-teens. Its premise is to render your framework on the server as much as you can and then serve that to the user so a lot of things can come pre-rendered already and cut the time to the first render with the added benefit of custom metadata per page. A very convoluted templating engine if you will.

Tools like Next.js are for some time now the default way and are even featured heavily in React documentation as the preferred method of using React. Apart from the abundance of security incidents plaguing Next.JS and the abysmal disregard for backwards compatibility, these "tools" or rather the Vercel platform are also very happy to extract hundreds of dollars yearly to give you some basic analytics and a fancy dashboard. A mediocre solution to a terrible problem they created and keep dragging everyone else with them.

Although Next offers a "static site generation", it is a secondary class citizen. It's meant to be hosted by them, paid by you monthly - that's the whole point.

React server side rendered components with hydration are an evolutionary dead end. They speed up the development a bit due to everyone knowing React and Next.JS being pushed as the default. That makes the ecosystem huge, but the tradeoff is horrible maintenance, constant fight with the browser lifecycle and the culture of extraction that platforms like Vercel bring with them.

Often when these projects get to a modest to large site, waiting for recompile in a local dev environment can take a noticeable amount of seconds (one such project i took over had a recompile time of 20-30 seconds) - just to see if that 4px margin makes it look better or not.

SSR Javascript + hydration is just wrong on a fundamental level.

RETVRN - to HTML, to CSS, to simple serving

There was a real gap in both standards and capabilities of contemporary browsers 10-15 years ago. That gap is no longer there.

Im talking about the most basic functionality, like the shitty <select>, layouting that required apprenticeship and years of practice (remember mason(ry).js lol?), CSS being basic and needing JS to fill in the role, tedious element selection forcing jQuery on everyone, etc. Well the good news is - all of these issues have been mostly or completely solved by now.

You do not need a fat client anymore. Let your browser be your fat client now.

And for the serving side: you will find it's MUCH cheaper to put static sites behind something like BunnyCDN or self-host your server. For even moderately visited websites its peanuts compared to paying the Vercel tax.
